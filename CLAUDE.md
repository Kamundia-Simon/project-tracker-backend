# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project overview

A workflow-driven **survey project tracking / CRM-style application** for 3Gem. Tracks a survey project from the moment a Project Manager picks it up from the sales pool, through scripting, QA, client approval, quota setup, fieldwork (soft launch → full launch), data processing, and final delivery.

This is folder name is a placeholder — rename freely once a real name is picked; nothing outside this repo depends on it yet.

**Primary design goal:** make it structurally hard to skip a step or lose track of who owns what, while keeping the workflow itself readable and free of unnecessary rigidity — reminders and gated confirmations over silent automation or hard blocks. See [`docs/decisions/`](docs/decisions/) for the reasoning behind each major call.

**Secondary goal — this is a deliberate learning project.** Prioritize readable code and explaining *why*, not just *what*. See "Working style" below.

## Tech stack

- **Backend:** Python / FastAPI, SQLAlchemy 2.0 + Alembic (migrations), MariaDB via PyMySQL
- **Frontend:** React + Vite + TypeScript, Tailwind CSS, shadcn/ui (components copied into the repo, not a black-box dependency — see `frontend/src/components/ui/`), TanStack Query for server state, react-router-dom
- **Auth:** Clerk — authentication only (who is this user). Authorization (what can they do) is entirely our own code — see [`docs/decisions/0003-db-driven-rbac.md`](docs/decisions/0003-db-driven-rbac.md)
- **Cache / rate limiting:** Redis, set up as part of the foundation layer (not bolted on later) — backs both `slowapi` rate limiting and short-TTL caching of expensive reads. See [`docs/decisions/0007-rate-limiting-and-caching.md`](docs/decisions/0007-rate-limiting-and-caching.md)
- **Fieldwork data:** pulled from a dedicated progress endpoint on the sibling `Cpi-Dashboard` project (../Cpi-Dashboard), polled on a schedule and stored as snapshots here — never duplicated, never queried live on every page load. See [`docs/decisions/0004-cpi-dashboard-integration.md`](docs/decisions/0004-cpi-dashboard-integration.md)
- **Deployment:** test environments on Vercel (frontend) + Railway (backend/DB); production is Dockerized on a Linux server (mirrors `Cpi-Dashboard`'s `Dockerfile` pattern)

## Working style — read this before writing any code

- **Build order changed 2026-10-22 — two horizontal passes with a hard stop at `LIVE`.** Pass A: every backend endpoint needed to drive a project from the pool to launched, verified end-to-end by `scripts/unittests.py`. Pass B: the design system and every frontend page covering the same ground. `LIVE` is the seam because everything before it is internal workflow this app owns, and everything after depends on the CPI Dashboard integration. See [`docs/phase-1-plan.md`](docs/phase-1-plan.md) for scope and the reasoning. **The vertical-slice rule still applies after Live** — the risk it guarded against (building endpoints no page ever consumes) is real and is being accepted deliberately for this one stretch, mitigated by the test script covering every endpoint's rejection paths as well as its happy path.
- The per-stage detail in the plan's original slice list is still accurate as *scope*; only the ordering changed.
- **The frontend design system is the second exception to slicing**, alongside the foundation layer: tokens → app shell → primitives, built once before any page. A design system built after three pages exist is a refactor of three pages, which is how an app ends up with three button heights. See [`docs/frontend-standards.md`](docs/frontend-standards.md) §0.
- **Installed design skills are advisory, not authoritative.** A marketplace of frontend design packs is installed (`frontend-stack` router, `impeccable`, `taste:*`, `emil-design-eng:*`, `ui-ux-pro-max:*`, and the `ui-reviewer` / `design-director` agents). Use `ui-reviewer` after significant UI work — it is genuinely good at contrast maths, semantics, state coverage and motion judgement, and has twice found real defects. Give it `frontend-standards.md` and `AUDIT.md` so it reviews against our standard. **Never load an aesthetic preset** (`taste:soft-skill`, `minimalist-ui`, `brutalist-skill`) — the direction is decided, and those packs will steer it. Precedence: the user's decisions → this project's docs → accessibility and correctness → the packs' taste. See [`docs/frontend-standards.md`](docs/frontend-standards.md) §0a for which pack positions were adopted and which were declined, with reasons.
- **No UI without the standard.** Every screen uses central tokens, the shared primitives and the documented spacing/type/radius/motion scales — never page-level styling, never a second version of an existing component. Status colour is a fixed vocabulary and never the only carrier of meaning. Mobile states are designed deliberately, not derived by shrinking the desktop layout. Stage and role names render through one central label map taken from the enums in `models.py`, never retyped per page.
- **Write the code, then explain what changed and why (from 2026-10-22).** Apply edits directly to files, then report: which files, what changed in each, and the reasoning behind any non-obvious call — the same depth of explanation as when the code was shown in chat first. The user reads the explanation to confirm alignment, so it has to be specific enough to catch a wrong decision without reading the diff. **The explanation is the point, not the code block** — this project exists partly so the user can follow *why* the code is shaped the way it is, and that obligation did not change when the mechanics did.
  - *Superseded:* until 2026-10-22 every new application source file was shown as a chat code block first and only written once the user said to. That slowed down once the conventions were established and the user could predict the shape of the code.
  - Still show first when a change is **genuinely contestable** — a new table, a workflow rule that contradicts an ADR, anything where the user's answer would change the design rather than the wording. Asking costs one message; unwinding a wrong migration costs more.
- Default to no comments in code; when a comment is warranted, one line explaining a non-obvious *why*, never a *what*.
- No premature abstraction — this is a small internal tool with ~20-25 users, not a multi-tenant SaaS product. Prefer three similar lines over a speculative shared helper.
- **Lightweight handover documentation.** Not excessive, but enough that someone else could pick this project up mid-build: a one-line module docstring at the top of each new file stating its role in the system (what it's responsible for, not how it works — the code itself shows how), and keep `docs/architecture.md`, `docs/phase-1-plan.md`, and the ADRs current as the primary handover reference, plus keep this file's "Repository layout" section (below) an accurate map of what actually exists, not a plan.

## Repository layout

**One repository** (restructured 2026-10-23), with `backend/` and `frontend/` as directories beside `docs/` and this file. It started as two sibling repos copied from `Cpi-Dashboard`'s pattern, which broke the moment they were pushed: `CLAUDE.md` and `docs/` sat above both, so cloning either repo lost every ADR and standard the work depends on. A monorepo also matches how the work actually lands — a checklist rule or a token change touches both halves in one go, and two repos would make that two PRs that can merge out of step.

Each half still keeps its own `.env` and its own `.gitignore`; Vercel and Railway both deploy from a subdirectory, so nothing about hosting requires the split.

- `backend/` — FastAPI + SQLAlchemy + Alembic. Foundation complete: `database.py`, `models.py` (14 Phase 1 tables), `schemas.py`, `constants.py` (static business vocabulary), `alembic/` wired to `Base.metadata`, plus `main.py`, `auth.py`, `dependencies.py`, `rate_limit.py`, `cache.py`. Five migrations applied against a local Docker MariaDB on host port `33306` (initial schema, `user_roles`, `survey_type`, `project_markets`/`change_requests`, UTC timestamps + `client_link_eta`); the company schema `dbtracker` now exists as the eventual target, reached by swapping `DB_URL` and re-running `alembic upgrade head`.
  - `project_markets` and `change_requests` are **schema ahead of endpoints** — the tables exist so the expensive migration happens before the history-bearing tables fill up, but the routes land in the slices that need them (markets in 3/6/7, change requests late in Phase 1). See `architecture.md` §16–§17 and ADRs 0009/0010.
  - `scripts/unittests.py` — end-to-end check of every endpoint built so far, success and failure paths. Needs the server running and the dev auth bypass on. Re-runnable, exits non-zero on failure. Run it after any change to a route or schema: `python scripts/unittests.py` from `backend/`. **This is the one application file to edit directly rather than showing in chat first** — it is test tooling, the user reads the results rather than the code, and every new endpoint should arrive with its checks already written.
  - `scripts/grant_role.py` — bootstrap path for granting a baseline role, straight through SQLAlchemy. Required because granting `admin` via the API needs `admin`, so the first administrator can never come from the API. Needed again on every fresh schema: migrations seed the roles, not who holds them.
  - **`routes/` — one file per resource, named after it, with the router prefix matching the URL.** `projects.py` → `/api/projects`, `clients.py` → `/api/clients`. The one deliberate exception is `reference.py` → `/api/reference`, which groups fixed vocabulary lists served from code (survey types, and later stages and role names) rather than a single table — the shared prefix signals to the frontend that nothing under it is writable. Resist the urge to file an endpoint under a loosely-related existing router because it's only three lines; a file name that no longer describes its contents is the first sign the grouping is wrong.
- `frontend/` — React + Vite + TypeScript + Tailwind v3 + shadcn/ui (Radix base, Mira preset, Phosphor icons). Theme tokens from preset `b7X65jeZhR` live in `src/index.css` as bare OKLCH components, mapped to Tailwind colours via `oklch(var(--x) / <alpha-value>)` in `tailwind.config.js` (see `docs/design-tokens.md`). Clerk + TanStack Query + Router providers wired in `main.tsx`; `App.tsx` is a header shell only — sidebar/navigation still to come. Only `components/ui/button.tsx` and `components/DevAuthToken.tsx` exist so far, so the design system in [`docs/frontend-standards.md`](docs/frontend-standards.md) is being established on an effectively blank frontend — no legacy screens to retrofit, and no excuse for a page that ignores it.
  - Intended structure, per `frontend-standards.md` §11: `src/styles/` or `index.css` for tokens · `src/components/ui/` for primitives (shadcn-copied, extended in place) · `src/components/layout/` for the shell · `src/features/<area>/` for feature components · `src/lib/` for the label maps, formatters and query client. Business logic stays out of presentation components where practical.
